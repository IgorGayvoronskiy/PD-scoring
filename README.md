<a id="s1"></a>
## 1. Причина

<a id="s1-1"></a>
### 1.1 Проблема

При рассмотрении заявки на предоставление кредита необходимо оценить риск дефолта заёмщика, чтобы снизить вероятность финансовых потерь банка. Требуется сервис, который автоматически рассчитывает оценку риска дефолта по информации, доступной на момент подачи заявки, и передаёт её в систему принятия кредитного решения.

<a id="s1-2"></a>
### 1.2 Бизнес-ценность

Более точная оценка кредитного риска должна позволить:

- снизить количество выдач высокорисковым клиентам;
- уменьшить кредитные потери;
- сохранить возможность выдачи кредитов надёжным клиентам.

Автоматизация процесса оценки риска также позволит сократить время обработки кредитной заявки.

<a id="s2"></a>
## 2. Работа сервиса

<a id="s2-1"></a>
### 2.1 Описание системы

Сервис получает на вход информацию о заёмщике и параметры кредитной заявки, доступные на момент её оформления (63 признака модели, см. [3.2](#s3-2)). На основании этих данных рассчитывается калиброванная оценка вероятности дефолта (`risk_score`). По значению `risk_score` заявка получает решение APPROVE, REVIEW или DECLINE (см. [2.3](#s2-3)), которое передаётся в систему принятия решения по кредиту.

Заявки поступают в сервис загрузкой CSV-файла, после чего все необработанные заявки оцениваются одним запуском скоринга. Для каждой оценки сохраняются версия модели, время ответа, решение и пять главных признаков, повлиявших на оценку (SHAP).

<a id="s2-2"></a>
### 2.2 Метрики

В качестве критериев успеха будут выступать следующие бизнес-метрики:

- **Default Rate** — отношение количества дефолтов к количеству выданных кредитов.
- **Expected Loss** — ожидаемые кредитные потери, рассчитываемые как:

  $$
  EL = PD \times LGD \times EAD,
  $$

  где:
  - `PD` — вероятность дефолта;
  - `LGD` — доля потери при дефолте;
  - `EAD` — задолженность на момент дефолта.

  > **Важно:** в используемом наборе данных нет достаточной информации для настоящих LGD и EAD. Поэтому можно использовать только приближение:
  >
  > `EL_proxy = risk_score × assumed_LGD × loan_amount`
  >
  > Это сценарная оценка для сравнения порогов и моделей. Нельзя выдавать её за реальные ожидаемые потери банка.

- **Approval Rate** — отношение количества одобренных заявок к общему количеству заявок.

  > **Важно:** это не настоящий Approval Rate кредитора. В наборе Lending Club находятся уже выданные кредиты, а полного потока отклонённых заявок нет. Поэтому это только условная симуляция порога.

От сервиса требуется снизить **Expected Loss** и **Default Rate** без существенного ухудшения **Approval Rate**.

<a id="s2-3"></a>
### 2.3 Разделение заявок на Approve, Review и Decline

Решение по заявке определяется двумя порогами `T_low` и `T_high` (`T_low ≤ T_high`):

```
risk_score < T_low                 → APPROVE
T_low ≤ risk_score < T_high        → REVIEW
risk_score ≥ T_high                → DECLINE
```

- **APPROVE** — риск низкий, заявка одобряется автоматически.
- **DECLINE** — риск высокий, заявка отклоняется автоматически.
- **REVIEW** — пограничная зона, решение принимает аналитик вручную.

Процесс обработки:

1. Модель считает `risk_score`, сервис применяет пороги и записывает решение вместе с предсказанием.
2. Заявки со статусом REVIEW попадают в очередь ручного разбора. Для каждой из них показываются пять признаков с наибольшим вкладом в оценку (SHAP) и направление этого вклада.
3. Аналитик переводит заявку в APPROVE или DECLINE. Переход возможен только из REVIEW, время ручного решения фиксируется, а заявка исчезает из очереди. Повторное решение по уже разобранной заявке отклоняется.

Пороги задаются параметрами модели и сохраняются вместе с ней в метаданных; сейчас заданы `T_low = 0.2027` и `T_high = 0.22`.

<a id="s3"></a>
## 3. Способ достижения поставленной цели

<a id="s3-1"></a>
### 3.1 Постановка задачи

Задача формулируется как бинарная классификация: по информации о заёмщике и кредитной заявке необходимо предсказать вероятность дефолта:

$$
\hat{p} = P(y=1 \mid X),
$$

где `y = 1` означает факт дефолта, а `X` — признаки, доступные на момент подачи заявки. Полученное значение $\hat{p}$ используется как оценка риска заявки (`risk_score`). Ограничения такой интерпретации описаны в разделе [4](#s4).

<a id="s3-2"></a>
### 3.2 Данные и признаки

Для обучения используется датасет, основанный на исторических кредитах Lending Club, выданных в период с 2007 по 2018 год. Он содержит 1 347 681 кредитную запись. Из исходного набора были исключены кредиты, находившиеся в промежуточных состояниях, поэтому в рассматриваемом датасете присутствуют только кредиты со статусами `Fully Paid` и `Charged Off`.

Целевая переменная `Default` преобразована в бинарный формат:

- `0` — кредит полностью погашен (`Fully Paid`);
- `1` — кредит перешёл в дефолт (`Charged Off`).

При обучении используются только признаки, которые были доступны на момент подачи кредитной заявки. Признаки, являющиеся результатом предварительной оценки кредитного риска самой Lending Club, например `int_rate`, `grade` и `sub_grade`, исключены, чтобы избежать использования готовой оценки риска в качестве входного признака. Дата выдачи `issue_d` используется только для временного разбиения и расчёта производного признака, но не является признаком модели.

Модель использует 63 признака в трёх группах:

| Группа | Признаки |
|---|---|
| Числовые (54) | параметры и доход: `loan_amnt`, `annual_inc`, `dti`; скоринг и история: `fico_range_low`, `fico_range_high`, `credit_history_months`; просрочки и негативные события: `delinq_2yrs`, `mths_since_last_delinq`, `pub_rec`, `pub_rec_bankruptcies`, `tax_liens`, `collections_12_mths_ex_med`, `chargeoff_within_12_mths`, `acc_now_delinq`, `delinq_amnt`, `num_accts_ever_120_pd`, `num_tl_120dpd_2m`, `num_tl_30dpd`, `num_tl_90g_dpd_24m`, `pct_tl_nvr_dlq`; запросы и новые счета: `inq_last_6mths`, `mths_since_recent_inq`, `acc_open_past_24mths`, `num_tl_op_past_12m`, `mo_sin_rcnt_tl`; открытые и общие счета: `open_acc`, `total_acc`, `num_sats`, `num_il_tl`, `num_op_rev_tl`, `num_rev_accts`, `num_actv_rev_tl`, `num_rev_tl_bal_gt_0`, `mort_acc`; возраст счетов: `mo_sin_old_il_acct`, `mo_sin_old_rev_tl_op`, `mo_sin_rcnt_rev_tl_op`; револьверные и банковские карты: `revol_bal`, `revol_util`, `total_rev_hi_lim`, `bc_util`, `bc_open_to_buy`, `num_bc_sats`, `num_bc_tl`, `num_actv_bc_tl`, `percent_bc_gt_75`, `mths_since_recent_bc`, `total_bc_limit`; балансы и лимиты: `tot_cur_bal`, `avg_cur_bal`, `tot_coll_amt`, `tot_hi_cred_lim`, `total_bal_ex_mort`, `total_il_high_credit_limit` |
| Категориальные (7) | `term`, `emp_length`, `home_ownership`, `verification_status`, `purpose`, `addr_state`, `application_type` |
| Категориальные с высокой кардинальностью (2) | `emp_title`, `zip_code` |

Производный признак `credit_history_months` считается как число месяцев между `earliest_cr_line` и датой выдачи `issue_d`. Для `emp_title` и `zip_code` значения нормализуются (пропуск заменяется на `missing`, пробелы обрезаются, регистр приводится к нижнему), остальные категории приводятся к строкам с тем же значением `missing` для пропусков. Числовые пропуски (например, в `mths_since_*` и блоке `num_*`) остаются пропусками, так как CatBoost обрабатывает их сам, а сам факт пропуска остаётся информативным.

Текстовые поля заявки (`title`, `desc`) в текущей версии не используются.

<a id="s3-3"></a>
### 3.3 Модель

В качестве baseline используется логистическая регрессия как интерпретируемая классическая модель кредитного скоринга. Её качество сравнивается с градиентным бустингом CatBoost, который выбран итоговой моделью: он работает с категориальными признаками (включая `emp_title` и `zip_code`) и пропусками напрямую.

Особенности обучения:

- **Классы.** Дефолтов существенно меньше, чем погашенных кредитов, поэтому используются сбалансированные веса классов (`auto_class_weights="Balanced"`). Это улучшает ранжирование, но искажает масштаб вероятностей.
- **Остановка обучения.** Early stopping выполняется по метрике Gini (`NormalizedGini`) на части валидационной выборки.
- **Калибровка.** Вероятности калибруются изотонической регрессией на отдельной части валидационной выборки, не участвовавшей в early stopping. Калибровка на данных, повлиявших на выбор модели, была бы оптимистичной. В сервис попадает калиброванная модель целиком.
- **Объяснения.** Вклад признаков считается с помощью SHAP по базовой модели CatBoost внутри калиброванной. Значения измеряются в лог-шансах базовой модели: знак и порядок признаков информативны, но это не вклад в калиброванную вероятность.

Модели версионируются в реестре MLflow. Каждая новая версия получает алиас `challenger` и становится `champion`, только если на одной и той же тестовой выборке улучшает Gini больше чем на заданный минимум, а PR-AUC и Brier Score при этом заметно не ухудшаются. Сервис загружает версию по алиасу `champion`.

<a id="s3-4"></a>
### 3.4 Валидация и метрики

Поскольку кредиты в датасете расположены во временном диапазоне с 2007 по 2018 год, для валидации используется временное разделение данных. Более ранние кредиты используются для обучения, а более поздние — для валидации и тестирования. Такой подход позволяет приблизить эксперимент к реальному сценарию применения модели на будущих заявках.

| Выборка | Период выдачи | Назначение | Размер |
|---|---|---|---|
| train | до 2015-12-31 | обучение | 826 604 |
| valid, часть 1 (`valid_es`) | 2016, первая половина по времени | early stopping | 146 547 |
| valid, часть 2 (`valid_calib`) | 2016, вторая половина по времени | калибровка | 146 548 |
| test | с 2017 по 2018 | финальная оценка | 225 611 |

Основной метрикой является **Gini**, которая оценивает способность модели правильно ранжировать клиентов по уровню риска:

$$
Gini = 2 \cdot ROC\text{-}AUC - 1.
$$

Дополнительной метрикой при выраженном дисбалансе классов используется **PR-AUC**.

Для оценки качества вероятностных прогнозов дополнительно проверяются **калибровка модели** и **Brier Score**.

<a id="s3-5"></a>
### 3.5 Оценка результата

После выбора модели проводится оценка на отложенном временном периоде и сравнение с baseline.

Качество модели оценивается по ML-метрикам:

- Gini (основная);
- PR-AUC;
- Brier Score;
- показатели калибровки.

Потенциальное влияние модели на бизнес оценивается по `EL_proxy`, Default Rate и Approval Rate при выбранных порогах (с учётом ограничений, описанных в [2.2](#s2-2)). Для этого рассчитываются доля заявок и фактическая доля дефолтов в каждой зоне решения. Это позволяет определить, способен ли новый подход снизить кредитные потери при сохранении сопоставимого уровня одобрения заявок.

<a id="s4"></a>
## 4. Ограничения текущей постановки

Текущую модель нельзя называть полноценной регуляторной PD-моделью. Для классической PD обычно задаётся конкретный период. Например: произойдёт ли дефолт в следующие 12 месяцев? В текущем наборе данных известен конечный результат завершённого кредита: `Fully Paid` или `Charged Off`, но нет одинакового фиксированного горизонта для каждого кредита.

Поэтому данную модель корректнее называть **моделью оценки риска кредитной заявки**, а её выход — `risk_score`, а не регуляторной вероятностью дефолта.

Связанные ограничения:

- Approval Rate является условной симуляцией порога, а не реальным показателем кредитора (см. [2.2](#s2-2)).
- Expected Loss считается приближённо как `EL_proxy` и пригоден только для сравнения порогов и моделей (см. [2.2](#s2-2)).

<a id="s5"></a>
## 5. Результаты

Модель CatBoost с изотонической калибровкой достигла **Gini = 0.43** и **PR-AUC = 0.389** на тестовой выборке.

Калибровка вероятностей проверена по таблице «предсказанное против наблюдаемого», **Brier Score = 0.152**.

Влияние порога на одобрения и потери: при **Approval Rate 44%** доля дефолтов среди одобренных составила **9%**, а ожидаемые потери (`EL_proxy`) — около **6.7%** от суммы выданных кредитов.

Эти цифры нужно читать с учётом ограничений, описанных выше: Approval Rate является условной симуляцией порога, а `EL_proxy` — сценарной оценкой, а не реальными потерями банка.

<a id="s6"></a>
## 6. Интерфейс сервиса

Интерфейс доступен по адресу: **https://pd-scoring.34-116-193-187.sslip.io/**

Он состоит из трёх вкладок.

**Applications**

- Загрузка CSV-файла с заявками.
- Таблица необработанных заявок.
- По нажатию кнопки **Run prediction** запускается процесс оценки всех необработанных заявок.

**Predictions**

- Просмотр оценок за период: сегодня, последние 7 дней, 30 дней, год или всё время.
- Для каждой заявки показываются время, оценка (`score`), решение, версия модели, время ответа и краткий набор признаков (`loan_amnt`, `term`, `purpose`, `annual_inc`, `dti`, `fico_range_low`).
- Выгрузка таблицы за выбранный период в CSV (с полным набором признаков и вкладами SHAP).

**Review**

- Очередь заявок с решением REVIEW, самые старые сверху. На вкладке показывается число заявок в очереди.
- Клик по заявке раскрывает под ней пять главных признаков с их значениями. Вклад каждого показан диаграммой.
- Переключатель **APPROVE / DECLINE** и кнопка подтверждения: после неё заявка исчезает из очереди, а новое решение отображается во вкладке Predictions.

Основные эндпоинты:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/predict` | оценка одной заявки (JSON) |
| POST | `/v1/applications/upload` | загрузка CSV с заявками |
| GET | `/v1/applications/unscored` | необработанные заявки |
| POST | `/v1/predict/batch` | оценка всех необработанных заявок |
| GET | `/v1/predictions?period=` | оценки за период (`today`, `week`, `month`, `year`, `all`) |
| GET | `/v1/predictions/export?period=` | выгрузка оценок в CSV |
| GET | `/v1/review` | очередь заявок на ручной разбор |
| POST | `/v1/review/{application_id}/decision` | решение по заявке из очереди (`APPROVE` или `DECLINE`) |
| GET | `/health`, `/ready` | состояние сервиса и загрузки модели |
